# การอนุมัติคำขอเป็นติวเตอร์

## วิธีใช้งาน

1. นักเรียนกดสลับเป็นติวเตอร์ ระบบเปิดฟอร์มเดียวกับแก้โปรไฟล์ แต่ยังไม่เปลี่ยนบทบาท
2. กรอกแนะนำตัว วิชา รูปแบบการสอน และช่องทางติดต่อ แล้วกด **ยืนยันและส่งคำขอ**
3. ผู้สมัครติวเตอร์จากหน้าสมัครสมาชิกกรอกข้อมูลการสอน และส่งคำขอพร้อมสร้างบัญชี
4. ระหว่างรออนุมัติ ผู้ใช้ยังเป็นนักเรียน กดปุ่มสลับเป็น **ติวเตอร์** เพื่อเปิดหน้าคำขอได้ ใต้ปุ่มจะแสดง **กำลังตรวจสอบ** ระหว่างรออนุมัติ
5. แอดมินเปิด **คำขอติวเตอร์** ตรวจข้อมูล แล้วเลือกอนุมัติหรือไม่อนุมัติพร้อมเหตุผล
6. อนุมัติแล้ว ผู้ใช้กดสลับเป็นติวเตอร์ได้ หากไม่ผ่านให้แก้ข้อมูลและส่งใหม่

## ฐานข้อมูลที่เปลี่ยนตามที่อนุญาต

เพิ่มใน `tutor_profiles` เพียง 3 คอลัมน์ ไม่สร้างตารางใหม่:

- `approval_status`: draft (ยังไม่ส่ง), pending (รอตรวจ), approved (อนุมัติ), rejected (ไม่อนุมัติ)
- `submitted_at`: เวลาส่งคำขอล่าสุด
- `reject_reason`: เหตุผลที่ไม่อนุมัติล่าสุด

Migration ตั้งติวเตอร์เดิมเป็น pending ตามที่ผู้ใช้เลือก ระบบจะเปลี่ยน current_role ที่ยังเป็น tutor กลับเป็น student เมื่อบัญชีนั้นส่ง request ครั้งถัดไป หากคำขอยังไม่ approved เพื่อกัน Session เก่าข้ามขั้นตอน

สำรองฐานข้อมูลก่อน migration ไว้ที่ `storage/app/tutor-approval-backup-20261013/database-before-approval.sqlite` ไม่ได้ลบโปรไฟล์ วิชา ช่องทางเรียน หรือนัดหมายเดิม

## การแบ่งโค้ด

- `TutorApplicationController`: เปิดหน้าฟอร์มและสถานะ
- `TutorProfileController`: ใช้การตรวจและบันทึกข้อมูลเดียวกับแก้โปรไฟล์
- `AdminTutorApplicationController`: รายการคำขอ รายละเอียด และผลตรวจ
- `EnsureTutorApproval`: กันบทบาทติวเตอร์ที่ยังไม่อนุมัติและทำให้ Session ตรงกับบัญชี
- `TutorApplicationNotification`: แจ้งแอดมินและผู้สมัครด้วยตารางแจ้งเตือนเดิม

ใช้ if, foreach, Blade และ Eloquent ตามรูปแบบเดิม มีคอมเมนต์อธิบาย `DB::transaction()` และ `lockForUpdate()` ในจุดที่ต้องกันการบันทึกซ้ำ ไม่เพิ่มประวัติการอนุมัติ

ไม่แก้โค้ด appointment/scheduling การตรวจสิทธิ์อยู่ในขั้นตอนสลับบทบาทและ middleware ของบัญชี
