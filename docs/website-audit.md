# ผลตรวจระบบ PeerTutor

วันที่ตรวจ: 13 ตุลาคม 2026

ตรวจการเชื่อม Route → Controller → Model → Blade และทดสอบการทำงานด้วยฐานข้อมูล SQLite ในหน่วยความจำ ไม่ใช้ฐานข้อมูลจริงในการทดสอบ ไม่เพิ่มตารางหรือคอลัมน์ และไม่รัน migration หรือ seeder ลงฐานข้อมูลจริงในงานตรวจครั้งนี้

## ระบบหลักที่มีอยู่และสิ่งที่ตรวจ

| ระบบ | สิ่งที่ตรวจ |
| --- | --- |
| สมาชิกและการเข้าสู่ระบบ | สมัครนักเรียน/ติวเตอร์ เข้าสู่ระบบ ออกจากระบบ ยืนยันอีเมล ยืนยันรหัสผ่าน และรีเซ็ตรหัสผ่านด้วย token |
| บทบาทและคำขอติวเตอร์ | นักเรียนส่งฟอร์มคำขอ รอแอดมินอนุมัติ ปฏิเสธพร้อมเหตุผล แก้ไขส่งใหม่ และป้องกันใช้บทบาทติวเตอร์ขณะรอตรวจ |
| โปรไฟล์และช่องทางติดต่อ | นักเรียนบันทึกวิชาที่สนใจ ติวเตอร์บันทึกข้อมูลการสอน ช่องทางติดต่อ รูปโปรไฟล์ และตรวจเจ้าของข้อมูล |
| รายวิชา ค้นหา และอันดับติวเตอร์ | ค้นหาชื่อและวิชา แสดงเฉพาะติวเตอร์ที่อนุมัติและบัญชีเปิดใช้งาน จัดอันดับ และจำกัดการแก้รายวิชาให้แอดมิน |
| รายการโปรด | แสดงเฉพาะรายการของผู้ใช้ เชื่อมหน้าโปรไฟล์ รองรับผู้ใช้ไม่มีโปรไฟล์ และ seeder ซ้ำไม่สร้างรายการซ้ำ |
| วิชาของฉัน | บันทึกวิชาที่สอน รูปแบบการสอน และช่องทางเรียนของเจ้าของบัญชี โดยไม่ลบรายวิชากลาง |
| จัดเวลาและตรวจเวลาตรงกัน | ตรวจ Service เดิมแบบไม่แก้ไฟล์ รวมช่วงเวลาติดกัน ตัดช่วงที่จองแล้ว ปฏิเสธช่วงซ้อน และเชื่อมข้อมูลเวลาเข้าฟอร์ม final |
| นัดหมายและห้องเรียน | ส่งคำขอ ยืนยัน/ปฏิเสธ ยกเลิก เสร็จสิ้นการเรียน ดูรายละเอียด ตรวจเจ้าของ และซ่อนช่องทางเรียนก่อนยืนยัน |
| รีวิวและคะแนนเฉลี่ย | ต้องเรียนเสร็จและเป็นเจ้าของนัดหมาย กันรีวิวซ้ำแม้แอดมินซ่อนรีวิว แก้/ลบรีวิว และคำนวณคะแนนเฉลี่ยใหม่ |
| รายงานปัญหา | เหตุผลจาก DB บันทึกรายงานจริง แอดมินเห็นรายการ กรองและปรับสถานะล่าสุด ตรวจสิทธิ์ และแสดงข้อความโดย escape |
| แจ้งเตือน | นัดหมายและรายงานส่งถึงบัญชีที่เกี่ยวข้อง นับเฉพาะของเจ้าของ อ่าน/ลบได้เฉพาะของตัวเอง และแจ้งผลรายงานกลับผู้ส่ง |
| แอดมิน | Dashboard ผู้ใช้ การระงับบัญชี คำขอติวเตอร์ รายวิชา เหตุผลรายงาน รายงาน รีวิว และรายการนัดหมาย |
| Settings | เปลี่ยนข้อมูล/รหัสผ่าน ลบบัญชีแบบ soft delete ตั้งค่า 2FA และตรวจความสัมพันธ์ passkeys |

## จุดที่แก้ในงานตรวจครั้งนี้

- การค้นหาติวเตอร์เคยอ้าง `users.username` ซึ่งไม่มีในตาราง เปลี่ยนเป็นชื่อและนามสกุลจริง และแยก query เป็นขั้นตอน
- แก้ namespace, trait, model และเส้นทาง view เก่าที่หน้า Settings/รีวิวอ้างผิด พร้อมลงทะเบียน Livewire namespace และ Review policy
- แก้ Settings เฉพาะ PHP ตามที่ได้รับอนุญาต คง HTML, CSS และข้อความหน้าจอเดิม
- ใช้ `user_id` เป็นคีย์ผู้ใช้ในการตรวจอีเมลและความสัมพันธ์ passkeys แทน `id` ที่ไม่มีในตาราง Users
- รีเซ็ตรหัสผ่านต้องตรวจ token ผ่าน Laravel Fortify และบันทึก password hash ยกเลิกเส้นทางที่เปลี่ยนรหัสผ่านได้จากอีเมลอย่างเดียว
- นัดหมายรองรับทั้งข้อมูลเก่าที่ใช้รหัส StudentProfile และข้อมูลใหม่ที่ใช้ User ID เพื่อให้หน้าแอดมิน หน้าแรกติวเตอร์ และรีวิวแสดงนักเรียนถูกคน
- การยืนยัน/ปฏิเสธตรวจสถานะ pending ภายใน transaction พร้อม lock เพื่อกันการส่งคำตอบพร้อมกัน
- รีวิวตรวจผู้เรียน ผู้สอน สถานะ completed และรายการที่ถูกซ่อนไว้ก่อนบันทึก เพื่อป้องกันรีวิวซ้ำ
- แก้การบันทึกโปรไฟล์นักเรียนและ Contacts ให้ใช้ชื่อคอลัมน์จริง ตรวจเจ้าของ และความยาวช่องทางติดต่อให้ตรงกับ DB
- จำกัดการเพิ่ม/แก้/ลบวิชาให้แอดมิน และป้องกันลบวิชาที่มีข้อมูลเชื่อมอยู่
- ปรับเฉพาะ PHP หน้าโปรไฟล์ฝั่ง final ตามที่ได้รับอนุญาต ให้เรียก `findSharedTimes()` เดิมและส่งเวลาว่างตรงกันให้ฟอร์มเดิม ไม่แก้ Service หรือ UI
- รองรับการอ่านรูปจาก public disk บนเครื่อง Windows ที่ไม่มี storage link พร้อมป้องกัน path traversal และแยก URL ของ private disk
- คืน `resources/css/app.css` เดิมจาก Git ตามที่ได้รับอนุญาต ติดตั้ง dependencies และ build assets สำเร็จ โดยไม่แก้การออกแบบ
- จัดรูปแบบ PHP นอกส่วนที่ห้ามแก้ แยกเงื่อนไข/query เพิ่มคอมเมนต์ภาษาไทย และนำโค้ดเก่าที่คอมเมนต์ทิ้งไว้ออกจาก AppointmentController

ยังคง transaction, validation, CSRF, การตรวจเจ้าของข้อมูล และการตรวจอนุมัติที่จำเป็น ไม่ลดกฎเหล่านี้เพื่อทำให้โค้ดสั้นลง

## ผลทดสอบล่าสุด

รันรวม `php artisan test --compact`: **105 รายการ ผ่าน 103 ไม่ผ่าน 2**, ตรวจ 627 assertions

- นอกชุดทดสอบ Scheduling: ผ่านทั้งหมด 82 รายการ (Feature 81 และ Unit ทั่วไป 1)
- ชุด Scheduling เดิม: ผ่าน 21 จาก 23 รายการ ไม่แก้ไฟล์ทดสอบในส่วนนี้
- Build assets สำเร็จ และ `git diff --check` ไม่พบข้อผิดพลาดช่องว่าง

รายการที่ยังไม่ผ่านทั้งสองอยู่ใน `tests/Feature/Scheduling/SchedulingIntegrationTest.php`:

1. บรรทัด 67 คาดหวัง `CSS/edit-profile.css` บนหน้านัดหมาย แต่หน้า UI ปัจจุบันใช้ stylesheet ของหน้านัดหมายเอง คำขอจองและการตรวจ DB/แจ้งเตือนก่อนถึงจุดนี้ผ่านแล้ว อย่างไรก็ตาม assertions ที่อยู่หลังจุดล้มเหลวใน test นี้ยังไม่ได้รัน
2. บรรทัด 130 คาดหวัง HTTP 422 เมื่อบัญชีติวเตอร์จองให้ตนเอง แต่ระบบปฏิเสธด้วย HTTP 403 เพราะบทบาทปัจจุบันไม่ใช่นักเรียน การป้องกันยังทำงาน แต่รหัสตอบกลับไม่ตรงกับ test

ไม่เปลี่ยน UI หรือกฎสิทธิ์เพื่อให้สองรายการนี้ผ่าน และไม่แก้ชุดทดสอบ schedule/availability ตามข้อกำหนดของผู้ใช้ จึงยังไม่ถือว่าชุดทดสอบทั้งเว็บผ่านทั้งหมด

## การรักษาไฟล์เดิมและข้อจำกัด

ตรวจ SHA-256 เทียบกับตอนเริ่มงาน: `app/Domains/Scheduling`, views ของ scheduling, tests ของ Scheduling, `config/scheduling.php` และ `TutorTeachingController.php` ไม่เปลี่ยน ส่วน UI เดิมไม่เปลี่ยน ยกเว้น PHP ใน Settings 3 ไฟล์ที่อนุญาตให้แก้ ซึ่งตรวจส่วน HTML หลัง PHP แล้วตรงกับเดิมทั้งหมด

ผลทดสอบยืนยันพฤติกรรมที่ครอบคลุมในชุดทดสอบ ไม่ได้ยืนยันทุกกรณีที่อาจเกิดขึ้นบนเครื่องจริง:

- ทดสอบเมลผ่าน mailer สำหรับทดสอบ ยังไม่ได้ส่งอีเมลจริงหรือยืนยันการตั้งค่า SMTP
- ยังไม่ได้ทดลองใช้อุปกรณ์ WebAuthn/passkey จริง หรือสแกน QR ด้วยแอป authenticator จริง
- ยังไม่ได้เข้าห้อง Zoom/Google Meet จริง การตรวจครอบคลุมข้อมูลและสิทธิ์แสดงลิงก์ภายในเว็บ
- การป้องกันคำขอซ้ำมีการตรวจสถานะและ transaction แต่ไม่ได้ทดสอบภาระงานหรือการส่งคำขอพร้อมกันจำนวนมาก
- ไม่เปลี่ยนข้อมูลใน DB จริง และไม่ commit หรือเปลี่ยนสถานะ merge ของผู้ใช้ในงานนี้
